“Counselign follows strict MVC on CodeIgniter 4.  
 
When a student books an appointment, the browser sends HTTP POST to Apache. The controller Student\Appointment::save() validates the session and form data. It writes through the database layer into the appointments table. The view only displays forms and lists — it never runs SQL.

  Slide 7 — Data Mining Algorithm & Why (Track D)

Duration: 60 seconds  
Speaker: [Member 1]  
Visual: Simple pipeline diagram (see Slide 4.2 in deck section)

    What to put on the slide

| Track D requirement | Algorithm / method | File |
|--------------------|--------------------|------|
| Classification | Lexicon-based sentiment (positive / negative / neutral) | app/Services/SentimentAnalysisService.php |
| Classification | Likert weighted mean → satisfaction band | app/Models/StudentFeedbackAnalyticsModel.php |
| Trend analysis | Time-series SQL aggregation (daily/weekly/monthly) — reports past data only | app/Controllers/Admin/DataAnalytics.php |
| Pattern recognition | Negative sentiment filter; pending feedback / peak load detection | FeedbackAnalytics, DataAnalytics |

    Full script

“Track D is embedded in the same database — not a separate spreadsheet tool.  
 
Classification — Sentiment: When a student submits feedback, SentimentAnalysisService tokenizes additional_comments, matches positive and negative lexicon words — including Tagalog — applies intensifiers like ‘very’ and negators like ‘not’, then assigns positive, negative, or neutral. Results are saved to sentiment_score (-100 to 100) and sentiment_label. We chose a lexicon approach because it is explainable to the panel, runs on XAMPP without GPU, and needs no large training set.  
 
Classification — Satisfaction: Likert ratings 1–5 are averaged into a weighted mean and mapped to bands: Very Satisfied (4.21–5.00) down to Very Dissatisfied (1.00–1.80) in StudentFeedbackAnalyticsModel.  
 
Trend analysis: DataAnalytics runs SQL GROUP BY on past appointments — counts per day/week/month. There is no predict() or forecast function in code today; admins infer next-period load from charts (e.g. “March had more bookings than February”).  
 
Pattern recognition: Admins filter negative sentiment feedback and view concentrations of pending_feedback appointments — operational patterns that need intervention.  
 
We will now demonstrate CRUD, relationships, and these intelligent outputs live.”

  Why Data Analytics is NOT “prediction” in code

You asked the right question. Here is the precise answer for defense.

    What “prediction” usually means in software

| Real prediction | What Counselign has today |
|-----------------|---------------------------|
| A function computes a future value (next week’s bookings, risk score, etc.) | None — no predict(), forecast(), or ML model |
| Output example: “Expected appointments next month: 42” | Output: “Last month had 38 appointments” (COUNT + GROUP BY) |
| Uses past data and a model/rule to project forward | Uses past data only to chart history |

DataAnalytics::getDailyAnalytics() (and related methods) run SQL like:

`sql
SELECT DATE(preferred_date) AS day, COUNT(*) AS total_appointments
FROM appointments
WHERE preferred_date >= DATE_SUB(CURRENT_DATE, INTERVAL 30 DAY)
GROUP BY DATE(preferred_date)
`

That is reporting, not forecasting.

    Why the old script said “prediction”

The Track D rubric gives an example: *“Predicting future outcomes from trends.”* The script stretched that to mean: “admins look at a trend chart and decide the future.” That is human inference, not system prediction. A strict panelist (or you) can correctly say: there is no prediction function.

    What Track D you *do* have in code (be honest)

| Rubric item | Implemented? | Where |
|-------------|--------------|--------|
| Classification | Yes | SentimentAnalysisService → positive / negative / neutral |
| Classification | Yes | StudentFeedbackAnalyticsModel::getInterpretation() → Satisfied bands |
| Prediction | No (automated) | Only planned in docs/DATA_ANALYTICS_PLAN.md |
| Pattern recognition | Yes | getNegativeFeedback(), peak counts, pending_feedback / pending_followup metrics |

    How to present Track D without overstating

Option A — Honest (recommended): Demo classification + pattern recognition strongly. For trends, say “trend analysis for decision support” and explain the admin infers the future from the chart.

Option B — Map sentiment trend as “prediction” (weaker but defensible): getSentimentTrend() shows if satisfaction is going down month over month — you can say the system indicates risk that service quality may worsen. Still historical, but closer to “outcome from trends.”

Option C — Add a real predict function (best for rubric): e.g. next month = average of last 3 months of total_appointments in DataAnalytics.php — then you can honestly demo “the system predicted X.”

    One sentence for the panel

“Our appointment analytics module is descriptive data mining today; automated prediction is on the roadmap. We meet Track D prediction through trend visibility plus admin planning, and through sentiment/satisfaction classification on feedback.”

  3.1 MVC Structure — Full Q&A

    Q: What is the difference between Model, View, and Controller in your project?

Answer:

“In Counselign, the View is only presentation — for example app/Views/student/student_schedule_appointment.php renders HTML and JavaScript. The Controller — such as Student\Appointment — receives HTTP requests, checks authentication, validates input, and decides what to return. The Model layer is our app/Models/* classes and CodeIgniter’s query builder, which execute database operations. We never put SQL inside views.”

    Q: Give a complete request example from login to booking.

Answer:

“1) Auth::login() validates credentials against users. 2) Session stores role and user_id. 3) Student opens GET student/schedule-appointment → Appointment::schedule() returns the view. 4) Form POSTs to student/appointment/save → Appointment::save() inserts into appointments. 5) Response JSON tells the UI success or error.”

    Q: Why CodeIgniter 4?

Answer:

“It provides built-in MVC routing, migrations, validation, and session handling. It deploys on XAMPP with PHP and MariaDB, which matches our school environment.”

  3.2 Database & Relationships — Full Q&A

Primary owner: [Member 2]

    Q: How is a student linked to an appointment?

Answer:

“appointments.student_id stores the student’s users.user_id (10-digit identifier), not necessarily the internal users.id integer. Controllers always filter by this key for student-facing queries.”

    Q: Why is PDS split into many tables?

Answer:

“Normalization reduces redundancy and mirrors official PDS sections: personal, academic, family, address, services needed/availed, etc. StudentPDSModel aggregates reads and uses BaseModel::executeAtomic() for multi-table writes.”

    Q: How do you ensure integrity?

Answer:

“InnoDB engine, foreign key migrations in app/Database/Migrations/, unique constraints where needed, and transactions on multi-step operations like feedback submit — transStart() in Feedback::submit() updates both student_feedback and appointments together.”

    Q: Where is the ERD?

Answer:

“docs/erd.md — Mermaid diagrams for core entities, PDS, and feedback.”

    Q: What is ACID in your system?

Answer:

“Atomicity: Feedback::submit() uses $db->transStart() — feedback insert and appointment status update commit or rollback together. Consistency: validation rules and foreign keys. Isolation: READ COMMITTED via TransactionManager. Durability: committed rows persist in InnoDB. See public/Misc/ACID_IMPLEMENTATION_SUMMARY.md.”

  3.5 Data Mining — Full Q&A

Primary owner: [Member 1]

    Q: Name your algorithms.

Answer:

“1) Lexicon-based sentiment analysis — rule-based classification. 2) Weighted mean + threshold bands — Likert classification. 3) SQL aggregation — GROUP BY time period for trends. 4) Threshold filtering — negative sentiment and pending feedback counts as pattern detection.”

    Q: How accurate is sentiment analysis?

Answer:

“We tested sample sentences: clear positive and negative phrases classify correctly. Neutral or sarcastic comments may default to neutral — we recommend human review for negative flags, which the admin UI supports.”

| Test input | Expected |
|------------|----------|
| Very helpful staff, thank you! | positive |
| Not satisfied with the wait | negative |
| Okay session | neutral |

    Q: Where is your prediction function?

Answer:

“We are transparent: DataAnalytics does not have a prediction function. It returns historical counts via SQL aggregation. The rubric’s ‘prediction from trends’ is met in our project as decision support — the system shows the trend; staff interpret it. Automated forecasting is listed in docs/DATA_ANALYTICS_PLAN.md Phase 3 but not built yet. Our classification (sentiment, Likert bands) and pattern recognition (negative feedback clusters) are implemented in PHP.”

    Q: Is that machine learning?

Answer:

“Sentiment uses rule-based lexicon classification, not neural networks. Appointment analytics are descriptive (COUNT/GROUP BY), not predictive functions. Formal forecasting is planned in docs/DATA_ANALYTICS_PLAN.md Phase 3 but not implemented in the current codebase.”

    Q: Why not use ChatGPT or deep learning?

Answer:

“Explainability for academic defense, no GPU dependency, data privacy kept on-premise on XAMPP, and small labeled dataset for counseling-specific text.”
